All exports are called via `exports['tLib']:FunctionName(...)`.

Exports are registered on the side that owns the state: menu pages and permissions on the
server, everything that draws on the client. Each section below says which side it is.

---

## Menu System

**Client and server.** One NUI menu shared by every resource on the server. tLib owns the
screen, the keyboard and the permission check; a consumer declares pages and handles rows.

Pages are registered on the **server**, because what a player may see is a server decision —
every open is answered with that player's own ACE-filtered tree. The **client** registers what
turns that tree into behaviour: handlers, presenters and hooks.

Menu IDs are namespaced: every page a resource registers must be `owner:name`. Every export
takes an optional trailing `declaredOwner`, used only where the platform cannot identify the
caller. Pass it as its own argument — never as the result of a call in the last argument slot,
since `f(json.decode(x))` expands to *two* values and the second lands in `declaredOwner`.

[Developing modular menu resources](/docs/tLib/menu-consumers) walks through a complete
standalone consumer.

### Server — declaring the tree

| Export | Description |
| --- | --- |
| `DefineMenuNamespace(spec)` | Required first. `{ ace, catalog?, order?, capabilities?, theme? }`. `ace` gates the whole namespace. |
| `RegisterMenuDomains(domains)` | Rate/cooldown domains actions may be assigned to. |
| `RegisterMenu(menu, definition)` | One page plus its authority. |
| `UnregisterMenu(menuId)` | Remove a page. |
| `RegisterMenuAuthority(spec)` / `UnregisterMenuAuthority()` | Answer for rows this resource does not own. |
| `OnMenuSnapshot(hook)` | Adjust a player's tree as it is built for them. |
| `RefreshMenus()` | Re-push every open menu. |

`definition` is `{ ace, actions = { [itemId] = { ace, run?, clientAction?, cooldown?, fixedValue?, domain? } }, theme?, rootVisible? }`.
`rootVisible = false` omits the automatic shared-root link without changing direct access or
permissions.

### Server — changing what is already registered

| Export | Description |
| --- | --- |
| `PatchMenuItem(menuId, itemId, changes)` | Patch one row. |
| `PatchMenuAction(itemId, changes)` | Patch one action; finds the page itself. |
| `SetMenuLinks(menuId, links)` | Replace dynamic submenu rows on a page you own. `{}` removes them. |
| `SetMenuItemVisible(itemId, visible)` | Show or hide a row. |
| `SetPlayerMenuOptions(source, itemId, options)` | One player's own choices for a selector. |
| `SetMenuNamespaceTheme(theme)` / `SetMenuTheme(menuId, theme)` | `nil` clears. |

### Client — behaviour

| Export | Description |
| --- | --- |
| `RegisterMenuActions(handlers)` | `{ [name] = function(value, context) end }`, installed as one table — all of it or none. |
| `RegisterMenuCatalogProvider(provider)` | Build this resource's catalog once, off a function that may yield. |
| `RegisterMenuHooks(spec)` | `{ snapshot, enter, leave, page, selection, close }`. `enter` may refuse a navigation. |
| `RegisterMenuPresenter(spec)` / `UnregisterMenuPresenter()` | Fill rows in as a page is presented. |
| `RegisterMenuStrings(dictionaries)` | Translations for this resource's rows. |
| `ConfigureMenuInterface(spec)` | The root page. One screen, so the last caller wins. |
| `SetMenuEffect(name, enabled, definition)` | A handler that keeps running after the row was activated, re-checked against the player's grants. |
| `PublishMenuItem(name, changes)` | Patch a row from the client. |
| `SetMenuItemState(name, value)` / `GetMenuItemState(name)` | Read and write a row's value. |
| `ExecuteMenuAction(name, value, context)` | Run an action as if the row was activated. |
| `OnMenuActionsCleanup(fn)` / `OnMenuActionsPersist(fn)` | Resource-stop hooks. |

### Client — the screen

Unscoped: the screen belongs to the player, not to a resource.

| Export | Description |
| --- | --- |
| `OpenMenu(menuId?)` | Re-checks the page against a fresh permission-filtered snapshot. Refuses while a menu is already up. |
| `CloseMenu()` | The same teardown the close key runs. Does not toggle — closing when nothing is open answers `false, 'Menu is not open'`. |
| `IsMenuVisible()`, `GetMenuStackIds()` | Current state. |
| `NavigateMenu(menuId)`, `InvalidateMenuContext()` | Move within the open tree. |
| `BindMenuKey(menuId)` | Claim a key-binding slot for a page; returns the command it runs under. |
| `SetMenuLocale(tag)` / `GetMenuLocale()` | Row translation locale. |
| `SetMenuAnchor(anchor)`, `SetMenuPalettes(value)` | Placement and colour presentation. |
| `PromptMenuText(title, initial, maximum, context)` | The game's own onscreen keyboard. Only from inside an action handler, whose `context` it needs. |

### A page

```lua
{ id = 'myres:tools', title = 'Tools', subtitle = ..., description = ..., parent = ..., items = { ... } }
```

## Dialog System

**Client.** Modal form dialogs with multiple field types. Results are delivered via local
events and via optional inline callbacks — the two are additive, not alternatives.

| Export | Description |
| --- | --- |
| `ShowDialog(id, opts)` | Open a dialog. Returns the resolved dialog `id`, or `nil, reason`. |
| `CloseDialog(id)` | Close an open dialog (fires the cancelled event). |
| `UpdateDialogField(id, fieldId, changes)` | Patch one field of a live dialog. |
| `UpdateDialogFields(id, changes)` | Patch several fields at once. |

### ShowDialog options

| Key | Type | Description |
| --- | --- | --- |
| `title` | `string` | Dialog heading. |
| `description` | `string` | Optional subheading. |
| `submitLabel` | `string` | Submit button label (default `"Submit"`). |
| `cancelLabel` | `string` | Cancel button label (default `"Cancel"`). |
| `size` | `string` | `"sm"`, `"md"` or `"lg"` (default `"md"`). |
| `theme` | `string` | Id of a registered tLib theme. |
| `blur` | `boolean` | Blur the scene behind the dialog. |
| `resetState` | `boolean` | Open at the defaults instead of where the player last left this dialog id. |
| `fields` | `table[]` | Array of field definitions. |

A dialog reopens **where the player left it**: the selected tab, each tab's scroll
position and where the panel was dragged to are remembered per dialog id, so closing
the dialog for a detour — a HUD reposition, a 3D editor — and reopening it lands back
on the tab the button was on. This needs no opt-in and applies to every consumer.

Values are never remembered, nor is validation state; a remembered tab that no longer
exists (config or permissions changed) falls back to the first tab. The state is held
in the NUI page in memory only, so restarting tLib or reconnecting forgets it. Pass
`resetState = true` for the rare caller that genuinely wants a first-run dialog.

### Field types

| Type | Extra keys |
| --- | --- |
| `text`, `number`, `password`, `textarea` | `placeholder`, `defaultValue`, `min`/`max` (number only) |
| `select`, `radio` | `options` (`{ value, label }[]`), `placeholder`, `defaultValue` |
| `slider` | `min`, `max`, `step`, `defaultValue` |
| `checkbox` | `defaultValue` (boolean) |
| `button` | `variant` (`default` / `primary` / `destructive`), `confirm` |

All fields share: `id` (required), `type`, `label`, `description`, `required`, `disabled`.

#### Confirming a dialog button

A `button` field fires `onButtonClick` the moment it is pressed. Give it a `confirm`
string and the press instead asks that question first, and only a second, explicit press
of **Confirm** fires the callback. Escape and **Cancel** both answer the question without
firing anything; the dialog itself stays open either way.

It is the same key, with the same meaning, as a menu row's `confirm` above.
`variant = 'destructive'` is colour and nothing else, so a button that cannot be undone
wants both.

```lua
{
    id = 'wipe',
    type = 'button',
    label = 'Clear all patterns',
    variant = 'destructive',
    confirm = 'Every pattern on this vehicle is deleted. This cannot be undone.',
}
```

One of each type in a single `lg` dialog. `select` with two options renders as a segmented
control rather than the `Dropdown` list:

<ZoomableImage

  width={1600}
  height={1018}
  alt="Dialog with text, number 12, masked password, notes textarea, a Tow/Release segmented select, a Mission Row dropdown, Day/Night, a Tint slider at 35 and a checkbox"

### Events

- `tLib:dialog:opened` — `(dialogId)`
- `tLib:dialog:submitted` — `(dialogId, values)`, `values` keyed by field `id`
- `tLib:dialog:cancelled` — `(dialogId)`

```lua
local dialogId = exports['tLib']:ShowDialog('my_dialog', {
    title = 'Player Info',
    fields = {
        { id = 'name', type = 'text', label = 'Name', required = true },
        { id = 'age', type = 'number', label = 'Age', min = 1, max = 120 },
        { id = 'role', type = 'select', label = 'Role', options = {
            { value = 'civ', label = 'Civilian' },
            { value = 'leo', label = 'Law Enforcement' },
        }},
    },
})

AddEventHandler('tLib:dialog:submitted', function(id, values)
    if id == dialogId then
        print('Name:', values.name, 'Age:', values.age, 'Role:', values.role)
    end
end)
```

## Toast / Notification System

**Client.** Non-interactable notifications that stack in a corner of the screen.

| Export | Description |
| --- | --- |
| `ShowToast(id, toastType, title, description, duration, theme)` | Show a toast. Returns the resolved `id`, or `nil, reason` at capacity. |
| `UpdateToast(id, changes)` | Merge changes into a live toast in place. |
| `DismissToast(id)` | Dismiss a single toast before it expires. |
| `DismissAll()` | Dismiss the calling resource's visible toasts. |

IDs are local to the producing resource: updates and dismissals cannot alter another
producer's notifications, and stopping a producer removes its persistent cards. A type change
or `duration = 0` restarts the type default; text- or theme-only updates keep the existing
deadline. Limits are 32 active per producer and 256 total.

### Types and default durations

| Type | Duration |
| --- | --- |
| `success` | 4000 ms |
| `error` | 6000 ms |
| `warning` | 5000 ms |
| `info` | 4000 ms |
| `loading` | Persistent until dismissed or updated |

Each type carries its own icon and colour, so the type you pass is what a player reads before
the words. Newest sits at the bottom of the stack:

<ZoomableImage
  src="/assets/tLib/toast--stack.png"
  width={1600}
  height={900}
  alt="Five stacked toasts: green Vehicle stored, red Not enough cash, amber Engine damaged, blue Shift starts in 5 minutes, and a spinning Installing layout"
/>

### Events

- `tLib:toast:shown` — `(id, toastType, title, owner)`
- `tLib:toast:updated` — `(id, patch, owner)`
- `tLib:toast:dismissed` — `(id, owner)`
- `tLib:toast:dismissedAll` — `(owner)`

```lua
exports['tLib']:ShowToast(nil, 'success', 'Saved', 'Your settings have been saved.')

local toastId = exports['tLib']:ShowToast(nil, 'loading', 'Saving...', 'Please wait.')
exports['tLib']:UpdateToast(toastId, { type = 'success', title = 'Done', description = 'Save complete.' })
```

**Client.** CSS variable–based themes, applied globally or scoped to one dialog, toast or
menu. One theme id themes all three surfaces.

| Export | Description |
| --- | --- |
| `AddTheme(id, opts)` | Register a theme, or replace one with the same id. Returns `true` on success. |
| `RemoveTheme(id)` | Unregister a theme. Returns `true` if it existed. |
| `SetTheme(id)` | Apply a theme globally. Pass `""` to clear. |
| `GetTheme(id)` | A copy of one theme definition, or `nil`. |
| `GetThemes()` | A copy of every registered theme, keyed by id. |

### AddTheme options

| Key | Type | Description |
| --- | --- | --- |
| `name` | `string` | Human-readable display name. |
| `description` | `string` | Optional description. |
| `cssVars` | `table` | CSS variable name → value. Keys must **not** include the leading `--`. |
| `extends` | `string` | Id of another theme to inherit from; these vars overlay it. |

- `tLib:theme:removed` — `(id)`

## HUD Layout

**Client.** Registers a resource's on-screen element with the shared HUD editor, so the
player can move, scale and hide it alongside every other resource's HUD.

| Export | Description |
| --- | --- |
| `RegisterHudComponent(id, options, fn)` | Register a draggable component. `fn(layout)` is called whenever its layout changes. |
| `UnregisterHudComponent(id)` | Remove it again. |
| `GetHudLayout(id)` | The component's current layout, or `nil`. |
| `SetHudLayout(id, layout)` | Move one of your own components from code. `true`, or `false, reason`. |
| `OpenHudEditor(options)` | Open the editor for this resource. `{ demo = true }` adds a sample component. |
| `CloseHudEditor()` | Close it, if this resource opened it. |
| `ResetHudLayout(id?)` | Restore factory placements and clear the saved record. With no `id`, everything. Returns how many components it restored. |

There is one editor, not one per resource. Registering puts your component in the same list,
and on the same screen, as everyone else's:

<ZoomableImage
  src="/assets/tLib/layout--editor.png"
  width={1600}
  height={900}
  alt="The HUD layout editor listing Lightbar HUD from tELS, Radio from tRadio and Radar from tRadar, with all three drag frames outlined inside a safe-area border"
/>

`SetHudLayout` returns `false, 'Close the layout editor first'` while the editor is open —
the editor is one transaction over every component, and **Cancel** would discard your write
along with the rest. Handle that refusal; do not retry in a loop.

`RegisterHudComponent` is refused the same way, for the same reason, and that one you do have
to come back from: a resource that starts while a player is positioning their HUD would
otherwise never register at all. Keep the definition and try again when the editor closes, or
register through `@tLib/shared/imports/hud/client.lua`, which does that for you.

For a `persist` component the record is written before your `fn` is called, so a `true` means
the position survives a reload.

`options` is `{ label, width, height, canHide?, canScale?, minScale?, maxScale?, persist?,
minVisiblePixels?, minVisibleFraction?, defaults = { x, y, scale, visible, anchor }, layout? }`.
Layouts persist per server endpoint; without one they are session-only and tLib says so at
startup.

### `defaults` and `layout` are different things

`defaults` is the **factory** placement — the one "Reset this" goes back to. `layout` is where
the widget **is right now**.

They only coincide for a component that has nowhere else to keep its placement. A consumer that
passes `persist = false` owns its own storage, and passing its saved position as `defaults` makes
Reset restore the very placement the player is trying to escape. If a widget can be dragged
somewhere it cannot be dragged back from, that makes it unrecoverable. Pass both:

```lua
exports['tLib']:RegisterHudComponent('radio', {
    label = 'Radio', width = 300, height = 440, persist = false,
    defaults = factoryPlacement,   -- where Reset puts it
    layout   = savedPlacement,     -- where it is
}, onLayout)
```

Pass both, always. There is no capability to probe for — pin `tlib_min_version '1.0'`, which
is the first release carrying `layout`. There is no `GetHudLayoutCapabilities()` export.

Every layout tLib is given — saved record, `layout`, or `defaults` — is validated independently
and falls through to the next when it is unusable, and the survivor is clamped against the live
resolution so at least `minVisiblePixels` (96 by default) or `minVisibleFraction` (0.4) of the
widget stays on screen. That happens on **registration**, not only while editing: a record
written at another resolution heals on the way in.

### Units

`x` and `y` are a ratio of a **1080px-tall reference screen on both axes** — the same unit the
widget's own size scales by — so a corner inset stays visually constant from 16:9 to 32:9.
Centre-anchored `x` is the one exception and stays proportional to the width. Dividing `x` by the
viewport *width* is the v1 rule and is wrong: at 3440x1440 it places the widget 3440/1440 = 2.39x
further from the anchor than the editor's outline, and drags stop being 1:1.

### If a player loses their HUD

`/tlibhud reset` restores every registered component to its factory placement and clears the
saved layout, with the editor open or shut, whichever resource opened it.

## Keybind registry

**Client.** The one place on the server where two *different* resources' key bindings are
visible at once. A resource's own `tlib.platform.keybindConflicts()` runs inside its own VM, so
it cannot see the collisions players actually hit: two resources that both default to `B`, both
firing on one press.

| Export | Description |
| --- | --- |
| `ReportKeybind(entry)` | Record one bind: `{ token, resource?, label?, default?, group? }`. `tlib.platform.bindKey` calls this for you. |
| `GetKeybinds()` | Every bind reported so far, as a flat array of `{ resource, token, label, default, group }`. |
| `GetKeybindConflicts()` | `{ { group, key, claims = { { resource, token, label, default, group }, … } }, … }`. |

Only `token` is required. `resource` defaults to `?`, `label` to the token, and `group` to
`keyboard`. A malformed entry is dropped rather than raised, so a bad call cannot break your
startup — but it also means a typo here is silent, and the bind simply never appears in
`GetKeybinds()`.

An entry with no `default` is recorded and never counted as a collision, and a conflict needs
**more than one resource** — two binds on one key from the same resource are left to that
resource's own `tlib.platform.keybindConflicts()`.

tLib prints its own report ten seconds after start, once. Resource start order is not
guaranteed, so a bind reported later is still recorded but misses that printout — call
`GetKeybindConflicts()` yourself if you need an answer after then.

Nothing here reassigns a key. The player's rebind is authoritative and FiveM stores it against
the command token, so act on a reported conflict by changing a **default** and shipping it, not
at runtime.

## Marketplace

**Client and server.** The in-game panel for browsing and installing content a resource
publishes.

| Export | Side | Description |
| --- | --- | --- |
| `RegisterMarketplaceType(kind, opts)` | Server | Declare a content type this resource provides. |
| `OpenMarketplace(opts)` | Client | Open the standalone panel. `{ resource = 'tRadio' }` scopes it to one product; `{ initialTab = 'sounds' }` picks the tab. |
| `ProvideMarketplaceData(opts)` | Client | Same payload, no modal: feeds a marketplace tab inside a dialog you already opened. |
| `CloseMarketplace()` | Client | Close the standalone panel. |

`ProvideMarketplaceData` is the integrated path. Give your dialog a tab with
`view = "marketplace"` and it renders the browser in that tab's panel, inside
your own dialog chrome. Call this when the server answers with what is
installed; it takes no NUI focus, because the dialog already has it.
`OpenMarketplace` stays for places with no host dialog to embed in.

## Logger

**Client and server.** Structured console logger with level filtering.

| Export | Description |
| --- | --- |
| `CreateLogger(loggerId, printFn, opts)` | Returns a log function pinned to a source name. `opts.minLevel` overrides the global level for that logger alone. |
| `Log(loggerId, args)` | Format and filter one line. Returns the formatted string, or `nil` when filtered or empty. |
| `SetLogLevel(level)` | Set the global minimum level. |

Levels: `1` DEBUG, `2` INFO, `3` WARN, `4` ERROR. A trailing number in the arguments is the
level; everything else is `tostring`'d and joined with spaces.

```lua
local log = exports['tLib']:CreateLogger('myresource', print)
log('Server started')           -- INFO
log('Debug details', 1)         -- DEBUG
log('Something went wrong', 4)  -- ERROR
```

`Log` returns the line and leaves the printing to the caller, for resources that route their
output somewhere other than the console:

```lua
local line = exports['tLib']:Log('myresource', { 'Something went wrong', 4 })
if line then print(line) end
```

## HTTP Helper

**Server.** Non-blocking requests through FiveM's native `PerformHttpRequest`. Separate from
tLib's public HTTP routing hub, which is documented in the README.

| Export | Description |
| --- | --- |
| `Fetch(opts, callback)` | Make an HTTP or HTTPS request. |

### Fetch options

| Key | Type | Description |
| --- | --- | --- |
| `url` | `string` | Required. Full URL including scheme. |
| `method` | `string` | HTTP method (default `"GET"`). |
| `headers` | `table` | Request headers as a key/value table. |
| `body` | `string` | Request body. |

Redirects are followed. There are no timeout or TLS-verification options: the native's
behaviour is used as-is.

**Callback:** `function(statusCode, body, headers, errorData)` — the native's response
arguments, forwarded unchanged. An HTTP error status is still a delivered response, so check
the status rather than assuming success.

```lua
exports['tLib']:Fetch({ url = 'https://example.com/api', method = 'GET' },
    function(status, body, headers, err)
        if status ~= 200 then
            print('Request failed:', status, err)
            return
        end
        print('Body:', body)
    end)
```

## Diagnostics consent

**Server.** Two exports, and a UI needs both. Everything crosses as a JSON
string, so a caller never has to branch on a type. See `tlib_telemetry` in
[Convars](/docs/tLib/convars#what-is-deliberately-not) for what is collected and
what deliberately is not.

| Export | Side | Description |
| --- | --- | --- |
| `GetTelemetryConsent()` | Server | `{ enabled, source, locked, convar, convarValue, queued, transport }`. |
| `SetTelemetryConsent(enabled)` | Server | `{ ok = true, consent }`, or `{ ok = false, reason, detail }`. |

```lua
local c = json.decode(exports['tLib']:GetTelemetryConsent())
```

⚠️ **Render a switch only when `locked` is false.** `locked` is true when
`tlib_telemetry` is set, and then the convar is the answer: there is nothing to
toggle, and a switch that appears to offer one is a control that lies. Show
`convarValue` and the `convar` name instead, so the operator can find what set
it. `source` is `convar`, `switch` or `default`.

⛔ **There is no `provisioned` field, and a UI must not render a "cannot
transmit" state.** The ingest authenticates with the same public key every studio
API call uses, so there is no credential for a consumer to resolve or report on.

⚠️ **Call `SetTelemetryConsent`, never the bundle's `DiagSetConsent` directly.**
This wrapper is what tells the already-connected clients; without that broadcast
a change takes effect for players who reconnect and for nobody else, which reads
as "the switch does nothing". It refuses with `reason = 'locked'` while the
convar has decided, rather than storing a preference that would be ignored.

⛔ It is **not** permission-gated here. A consumer exposing it to players must
gate it at its own call site.

⛔ **And never on an unauthenticated surface.** tLib's own hub binds `0.0.0.0` by
default and its index carries no auth, so it calls neither of these and shows no
diagnostics state at all. For an operator, `tlib_telemetry` is the only control.

`tlib_telemetry_status` on the server console prints the same answer, plus the
queue depth and whether the transport has given up.

## Local inference

**Server.** For resources that ship their own model runtime. Everything crosses as a JSON
string, and an empty string is the universal "no".

| Export | Description |
| --- | --- |
| `InferenceAdvertise(json)` | Register an engine you started: `{ capability, workload, url, model }`. Returns a handle. The URL must be on `127.0.0.1`. |
| `InferenceLookup(capability, workload)` | An engine another resource already has up for the same weights, or `''`. Never returns your own. |
| `InferenceWithdraw(handle)` | Drop one of your own advertisements. A resource's entries are dropped for it when it stops. |
| `InferenceList()` | Everything registered, for diagnostics. |

Starting those engines is a separate, gated surface — see [Child processes](#child-processes).

## Child processes

**Server.** One `add_unsafe_child_process_permission` line for a whole box, however many
resources on it ship a local engine.

FXServer attributes the child-process check to whichever resource's runtime made the call, so
without this every resource that spawns would need its own grant. tLib makes the call instead,
so the only line you need is:

```cfg
add_unsafe_child_process_permission tLib
```

### What sits behind the one line

**The caller names a program, never a path.** tLib holds a catalog of which resources may
spawn, which programs each may run, where those programs live inside that resource, and what
their arguments are allowed to look like. It resolves the executable itself, checks the
resolved path is inside the calling resource after `realpath` (so neither a `..` nor a symlink
escapes), rebuilds the argv token by token from a declared shape, and execs with **no shell**.

So what tDB can run through this grant is `pocketbase`, from its own directory, with
PocketBase's own flags — not an arbitrary command line.

<Callout type="warning">
This narrows what a **compromised first-party resource** can do. It is not a defence against a
hostile resource *pretending* to be one. `GetInvokingResource()` identifies the calling
resource container honestly, but a folder named `tDB` containing someone else's code passes
that check — exactly as it passed `add_unsafe_child_process_permission tDB` before. The
`author` in a caller's fxmanifest is read and a mismatch is logged loudly, but a resource
writes its own manifest, so a match authorises nothing and nothing in tLib branches on it.
</Callout>

### Exports

| Export | Description |
| --- | --- |
| `SpawnServe(json)` | Start a long-lived process: `{ key, program, args, cwd, env, mode }`. Returns `{ pid }` or `{ error }`. Serving the same `key` twice while it is alive returns the first pid rather than a second copy. |
| `SpawnOutput(key, since)` | `{ lines, next, alive, code }` — what that process has printed since your cursor. In `bytes` mode, `{ chunks, next, stderr, alive, code }`. |
| `SpawnUnserve(key)` | Stop it: SIGTERM, then SIGKILL after a five-second grace. |
| `SpawnWrite(key, base64)` | Write bytes to a `bytes`-mode process's stdin. |
| `SpawnRun(json)` | A one-shot: `{ program, args, cwd, env, stdin }`. Returns `{ job }`. |
| `SpawnJob(id)` | `{ state, code, stdout, stderr, error }`. Reading a finished job forgets it. |
| `SpawnCancel(id)` | Kill a one-shot that is still running. |
| `SpawnList()` | What is running and for whom, for diagnostics. |

`cwd` is resource-relative and must be one the catalog declares for that program; omitted, it
is the binary's own directory. `env` names must be on the program's allowlist — this is why
`LD_PRELOAD` cannot be set. `mode` is `lines` (default) or `bytes`, which hands stdout back
base64 with nothing dropped and keeps stdin open; it exists for a child that exchanges binary
frames rather than log lines, and it widens the **data** path only — the program, its path and
its arguments go through the same gate either way.

### Cross-platform

There is no platform branch in this surface. The catalog declares a binary per platform —
tDB's `.runtime/pocketbase-win.exe` against `.runtime/pocketbase-linux` — and the caller never
says which one it wants.

Containment compares paths **exactly**, never case-folded: `/opt/res/tdb` and `/opt/res/tDB`
are two directories on Linux, so folding them would accept the wrong one there while weakening
the check on Windows.

Nothing here shells out to PowerShell, so a minimal Linux container needs no extra packages.

### Lifecycle

A child started here belongs to **tLib's** runtime, not to the resource that asked for it, so
it no longer dies with its owner for free. tLib reaps it instead:

- when the owning resource stops — including the stop half of a restart;
- when the owner calls `SpawnUnserve`;
- when tLib itself stops, because a restart that left them running would find its own ports
  held by its own children.

A caller restarting is **kill-and-respawn, not reuse**. `onResourceStop` fires before the
restarted copy starts, so the old engine is signalled and waited for before a new one is asked
for. Expect a fresh process: a restarted resource may want a different model, context size or
port, and none of those would reach an adopted one.

Watch for orphans. A leftover PocketBase holds its HTTP port and locks its SQLite directory,
and the next start then fails as a bind error that reads like misconfiguration. Keep your own
PID file too — it is the only thing that covers the *unclean* case, since `kill -9` and txAdmin
give neither resource a chance to run a handler.

### Binary integrity

The spawn catalog supports a `sha256` list per program, and nothing uses it today. These
binaries are verified where they are fetched, not where they are run:

- PocketBase **updates itself**, so its hash changes underneath any pin tLib could ship.
- `llama-server`, `whisper-server`, `piper` and the vendored Node are fetched per platform and
  per upstream release by each resource's own setup script, which verifies them against the
  publisher's checksums *at fetch time*.

What this gate adds on top is containment and argument shape, not integrity.

## Utilities

| Export | Side | Description |
| --- | --- | --- |
| `GenerateId()` | Both | A unique id string, the same generator tLib uses for dialogs and toasts. |
| `Platform()` | Client | tLib's platform adapter, as a table of callable references. |
| `CreateDiscovery(opts)` | Server | Scan resources for tagged config files, load and save them, and pick up resources that start late. |
| `CreateServerSettings(opts)` | Server | Admin-configurable settings for one resource, persisted to a JSON file inside it. |
| `CommunityConfigsImport(...)` / `CommunityConfigsUpload(...)` | Server | Proxy for the community configs API, so a consumer neither repeats the HTTP boilerplate nor sees the server hash. |
| `CommunityConfigsPeek(id, cb)` | Server | The same config payload `CommunityConfigsImport` returns, but it does **not** increment the config's import counter. Use it to render or preview a listing; use `CommunityConfigsImport` only when a player actually installs one. |
| `CommunityConfigsList(opts, cb)` | Server | Browse published configs. `opts` is `{ script, configType, key?, limit? }` — the first two are required, `limit` defaults to `30`. `cb(ok, items, err)` with `items` already decoded. |
| `CommunityConfigsMatch(opts, cb)` | Server | **Candidates** for a vehicle, by model fingerprint. `opts` is `{ fp, script?, configType?, key?, limit? }`; `fp` is required, `configType` defaults to `led_layout`, `limit` to `30`. Same `cb(ok, items, err)`. |
| `IsDemoMode()` | Server | `true` while `tlib_demo` is on. The export behind `tlib.demo.active()`. |

`CommunityConfigsMatch` returns **candidates, not matches**. Each item carries the
publisher's own fingerprint in `fp`; comparing it is yours to do.

Call both from the game server, never from your NUI. `/api/v1` sends no
`Access-Control-Allow-Origin`, so a `fetch` from `cfx-nui-<resource>` is refused by the browser
*after* the request has already succeeded.

`CreateDiscovery` must be given `resourceName = GetCurrentResourceName()` when it is called at
module init time: `GetInvokingResource()` returns `nil` during top-level script execution, and
without the name the file I/O targets tLib instead of the caller.

## Exporting a config into another resource

Discovery can move a config out of your resource's `data.json` and into the resource that owns
the model — a vehicle pack ships `tels.json` beside its `.yft`, declares it in its own
`fxmanifest.lua`, and the config travels with the vehicle instead of living in a server-specific
data file.

That write crosses a resource boundary, which FiveM constrains — but does not forbid.

<Callout type="warning">
FiveM sandboxes a write to the resource it **originates in**, not to the one it lands in. From
one resource's runtime, `SaveResourceFile` into your **own** resource returns `1`, into
**another** started resource returns `false`, and into a resource that does not exist **raises**.
Node's `fs` behaves the same way. Reads are not restricted — `LoadResourceFile` works everywhere.
</Callout>

So the write has to be performed *by the destination*. Every resource that bundles tLib's
`shared/ts` registers its own `WriteResourceFile` export, and a FiveM export is callable across
resources, so tLib asks the target to write its own file. Nothing is ever reported as exported
unless the file actually landed.

<Callout type="warning">
**No `server.cfg` line changes this — do not add one.** `add_filesystem_permission tLib
write *` looks like the fix and does nothing: the sandbox is not asking about permission, it is
asking which resource is writing. `--allow-fs-write` is a server *launch argument*, so it is
not open to you either. If that line is already in your config, delete it.
</Callout>

Which of the two paths below you get is decided by the target, not by your configuration.

### When the target runs its own code

Any resource with a server bundle that calls `registerWriteResourceFile()` from
`tLib/shared/ts/fs/server.ts` accepts the export directly.
tLib writes the JSON into it and adds the metadata line to its `fxmanifest.lua` for you. One
click, nothing to copy.

### When the target is a plain asset pack

A vehicle pack is usually just models and a `tels.json` — no scripts, no bundle, so there is no
runtime inside it to perform the write. That case cannot be configured away. tLib writes the
**finished file** into its own directory instead and tells you exactly what to do with it. The
player sees the
steps in chat and the server console logs the same three lines:

```
1. Copy tLib/export-staging/<target-resource>/<file>.json  ->  <target-resource>/<file>.json
2. Add this line to <target-resource>/fxmanifest.lua:  tels_config 'tels.json'
3. Restart <target-resource> (or the server).
```

The staged file is not a fragment — it is the target's existing config file with your model
merged into it, so it can be dropped straight in. Until you do, nothing has changed: the config
is still local, still served to clients, and the picker still shows it as local.

### What the metadata line looks like

The key is whatever the consuming resource declares — `tels_config` for tELS, `tradio_config`
for tRadio — and the value is the file name relative to the resource root:

```lua
-- fxmanifest.lua, in the vehicle resource
tels_config 'tels.json'
```

Without that line the file is never read, however it got there.
