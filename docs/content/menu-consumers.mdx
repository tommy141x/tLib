A consumer declares pages on the server and handles rows on the client.

| Owner | Owns |
| --- | --- |
| tLib | Schema, rendering, navigation, authority, dispatch, state/effects, the shared adapters. |
| Consumer | Feature behaviour, menu declarations, configuration, commands, its own state. |
| Optional host | Public slots, placement policy, allowlists, ordering. Hosting does not make it the engine. |

Do not call another consumer's private functions, inject its actions, or configure the
shared screen from every plugin. `ConfigureMenuInterface` is shared player-UI policy, not
plugin branding; use namespace or page themes for a consumer's visual identity.

## A minimal consumer

```lua title="fxmanifest.lua"
fx_version 'cerulean'
game 'gta5'
dependency 'tLib'
tlib_min_version '1.0'
shared_script '@tLib/imports.lua'
server_script 'server.lua'
client_script 'client.lua'
```

```lua title="server.lua"
local owner, menu = GetCurrentResourceName(), exports['tLib']
local lifecycle = tlib.lifecycle
assert(type(lifecycle) == 'table' and lifecycle.version == 1, 'Update tLib: lifecycle API v1 required')
lifecycle.watch({ resource = 'tLib', install = function(ctx)
    ctx.once('namespace', function()
        return menu:DefineMenuNamespace({ ace = 'mytools.use' })
    end)
    ctx.once('page', function()
        return menu:RegisterMenu({
            id = owner .. ':tools', title = 'Tools', parent = 'main',
            items = {{ id = owner .. ':hello', label = 'Hello', kind = 'action' }},
        }, {
            ace = 'mytools.use', rootVisible = true,
            actions = { [owner .. ':hello'] = { ace = 'mytools.use', clientAction = 'hello' } },
        })
    end)
end })
```

```lua title="client.lua"
local owner, menu = GetCurrentResourceName(), exports['tLib']
local lifecycle = tlib.lifecycle
assert(type(lifecycle) == 'table' and lifecycle.version == 1, 'Update tLib: lifecycle API v1 required')
local registration = lifecycle.watch({ resource = 'tLib', install = function(ctx)
    ctx.once('actions', function()
        return menu:RegisterMenuActions({ hello = function()
            menu:ShowToast('hello', 'info', 'Tools', 'Hello!')
        end })
    end)
end })
RegisterCommand('mytools', function()
    if not registration.ready() then return end
    local ok, reason = menu:OpenMenu(owner .. ':tools')
    if not ok then print(reason) end
end, false)
```

Grant `mytools.use` to the group that should have it. The server still checks the
namespace, page and action ACE — a command or keybinding opens a page, it does not
authorize one. Decode data into locals before passing it as an export's last argument: a
multi-return Lua function can fill the optional `declaredOwner` parameter.

## Shared lifecycle adapter (API v1)

`tlib.lifecycle.watch({ resource, install, cleanup?, readyEvent? })` runs in the consumer
VM, so its subscriptions survive a dependency restart.

| Returns | Description |
| --- | --- |
| `ready()` | Registration completed for the current dependency generation. |
| `retry()` | Request a new bounded attempt, if not already busy or ready. |
| `invalidate()` | Cancel pending work, clear step checkpoints, invoke `cleanup`. |
| `dispose()` | Invalidate and release event subscriptions. Idempotent. |

It watches the correct server/client resource events, waits a scheduler tick before
registering, retries up to 300 times 100 ms apart, and reports the real last error. There is
no indefinite idle loop and no network event is registered. A supplied `readyEvent` must
carry the dependency's resource name as its first argument; unrelated events are ignored.

`install(ctx)` should throw on failure. `ctx.once(name, fn)` requires `fn` to return `true`
(or `false, reason` to fail) and skips successful steps on later attempts in the same
generation — one step per non-idempotent registration. All steps reset on dependency stop,
and duplicate start/readiness events do not reinstall. `ctx.isActive()` lets yielding setup
code check its lifetime.

<Callout type="warning">
This is **not a transaction and not automatic rollback**. Successful registration steps
remain until the dependency removes them or the owner stops. `cleanup` must be idempotent
and restore consumer-owned native state, and must not assume the stopped dependency's
exports are available.
</Callout>

Avoid native gameplay effects in registration; use authorized actions and `SetMenuEffect`
for ongoing behaviour and revocation cleanup. An exhausted registration can retry on a later
readiness event or an explicit `retry()`.

Assert the **import** version — `lifecycle.version`, `menuhost.version` — as both examples
do. The resource's own `version` in `fxmanifest.lua` moves for any change, so it cannot tell
you which local API additions a checkout has. These are Lua APIs and need no UI build, but
reload the resource to run changed Lua.

## Optional host (API v1)

Any server resource can expose navigation slots:

```lua
local host = tlib.menuhost
assert(type(host) == 'table' and host.version == 1, 'Update tLib: menu host API v1 required')
host.install({
    ['tools.extensions'] = {
        menu = GetCurrentResourceName() .. ':tools',
        enabled = true,
        -- resources = { somePlugin = true },
        -- order = { ['somePlugin:entry'] = 10 },
    },
})
```

Install once, after declaring the host's pages. It exposes the host-scoped server exports
`RegisterPluginMenu({ id, slot, menu, label, description? })` and `UnregisterPluginMenu(id)`,
calling tLib's owner-only `SetMenuLinks` from the host VM. It never grants another resource
authority to replace host actions. Readiness is `tlib:menu:hostReady(hostResource)`.

A plugin watches its configured host with the lifecycle adapter and calls
`RegisterPluginMenu` in a checkpointed step after registering its own target page. The same
owner and id replaces an existing link, so retrying is safe, and only the calling resource's
namespace may be targeted. Host policy controls allowed callers and ordering; player
permissions are checked independently by tLib.

The host adapter composes slots sharing a page, so do **not** also write that page's dynamic
link collection with `SetMenuLinks`. When the engine restarts, consumers recreate their own
pages and host links: invalidate the host-link watcher when engine registrations are lost,
then retry it after the page has registered.

## Placement is not permission ancestry

`RegisterMenu(page, { ace, actions, rootVisible = false })` suppresses only the automatic
shared-root link. It does not hide the page from authorized direct access, host links or
search, and it changes no permission. Omit it or use `true` for a root entry.

Keep an independently usable page parented to `main`. Parenting it to a host page also makes
that host's ancestor permissions mandatory, including for direct command access.

## The shared "Send feedback" row

tLib adds one row of its own to **every namespace's entry page** — the page whose `parent`
is `main` or absent. You do not register it and cannot: the row and its dialog live in
tLib's own browser bundle, which every menu renders through.

<Callout type="warning">
**It is not one of your rows.** It is a client-side synthetic row, like a cross-menu search
hit: no ACE, no action handler, no item id in your catalog, and it never reaches
`resolveAction`. A parity test counting rows on an entry page sees one more than it
registered; a snapshot assertion does not, because the row is added in the browser, after
the wire.
</Callout>

The dialog sends the player's message to TIMMYG Studios with the resource name, its manifest
`version`, and tLib's random per-install id. Nothing else — no player name, licence, Steam
or Discord id, no server name, no IP.

- **It does not need telemetry consent** and is unaffected by `tlib_telemetry`. The
  per-install id is sent either way, because it accompanies every request tLib makes to
  timmygstudios.com, so a message is attributable to an install but never to a person. See
  [Convars](/docs/tLib/convars#diagnostics).
- **It is not permission-gated**, and no ACE hides it. Feedback is about the software, not
  about the server.

It appears only on an entry page, is hidden while the player is filtering, and a page with
no `owner:` prefix — the shared `main` root — gets no row.

## Verifying a consumer

In-game checks must cover initial startup, dependency restarts, late host availability,
permission loss, direct access, root-hidden navigation and NUI focus. Mocked tests cover
native state cleanup and lifecycle transitions and never visual correctness, so do not infer
live success from them. Refresh resource discovery before an authorized reload or start —
source edits alone do not update a running resource.
